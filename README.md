# TutorSat

A full-stack SAT-style practice platform where **question selection is driven by two
real statistical models**: a Dirichlet-multinomial blueprint over the published
digital SAT framework, and a 2-parameter-logistic IRT ability estimator that adapts
to the user in real time.

## Quick start

Requires **Python 3.10+** (standard library only: zero dependencies).

```bash
python run.py                # serves http://127.0.0.1:8765
python run.py --port 9000 --db mydata.db
```

Open http://127.0.0.1:8765 in a browser: create a profile → practice → mock → dashboard.

Run the test suite (92 tests):

```bash
python -m unittest discover -s tests -v
```

Reset all data by deleting `satprep.db`.

### Optional: Google Sign-In

Local profiles work out of the box. If you want Google account sign-in:

1. Create an OAuth **client ID** (type: Web application) in Google Cloud Console,
   and add `http://localhost:8765` (and any other origin you serve from) to its
   **Authorized JavaScript origins**.
2. Start the server with it:
   `python run.py --google-client-id YOUR_CLIENT_ID.apps.googleusercontent.com`
   or set the `GOOGLE_CLIENT_ID` environment variable.
3. The onboarding screen gains a "Sign in with Google" button. Successful
   sign-ins map your Google account to a stable local account id (`g-…`), so θ
   history persists across logins.

Implementation notes: verification is real and dependency-free. The ID token's
RS256 signature is checked against Google's published JWKS (RSA verify via
Python big-integer math), and `iss`, `aud`, `exp`, and `sub` claims are all
enforced server-side. Without a client ID configured, the button never renders
and `/api/auth/google` refuses requests; only profile fields (name, email,
subject) are read.

#### How your data links to the Google account

- Google returns an immutable `sub` (subject) claim. The server derives your
  account id deterministically: `g-<sha256("google:" + sub)[:16]>`. Every θ
  estimate, response, and session row is stored under that id.
- Practical effect: sign in on any browser or device pointed at the same
  deployment and you land on the same history. Nothing is stored on Google's
  side; all data lives in your deployment's SQLite file.
- **Claiming prior local progress:** progress made before signing in lives
  under an anonymous `u-*` id for that browser. At Google login the app probes
  for it and asks once: "Link your local progress?" Accepting re-parents those
  sessions to the `g-*` account and re-fits every θ over the combined response
  log, so estimates stay mathematically exact. Declining starts fresh; the
  anonymous history stays on that browser.
- Security note: linking requires a fresh, verified Google credential for the
  destination account. Knowing someone's account id string alone grants no
  access to its data.

## Methodology

### Model 1: Blueprint model (`satprep/core/blueprint.py`)

**Approach note.** The blueprint layer applies two much older, general-purpose
techniques to the SAT's published structure: the **Dirichlet-multinomial conjugate
model** (the standard Bayesian treatment of categorical proportions) and
**Hamilton's largest-remainder apportionment** (how legislatures and parliaments
have turned proportional votes into fixed seat counts since the 1790s). Neither
technique originates here, and independent test-prep projects have combined them
for SAT planning in their own ways. This implementation was written from those
textbook foundations with its own choices throughout: a κ=400 concentration,
SHA-256-derived seed streams rather than date seeding, hierarchical
skill-within-domain and difficulty layers, observations keyed at leaf granularity,
and integration with a per-skill 2PL IRT engine that drives question selection.
It forecasts nothing about future administrations; it composes practice sessions.

**State space.** The framework tree (`core/framework.py`) is flattened into leaves
`(section, domain, skill, difficulty)`. Section-level domain weights and within-domain
skill weights are author-encoded from publicly documented digital SAT specs
(Reading & Writing ≈ Craft & Structure 28% / Information & Ideas 26% / Standard English
Conventions 26% / Expression of Ideas 20%; Math ≈ Algebra 35% / Advanced Math 35% /
Problem-Solving & Data Analysis 15% / Geometry & Trigonometry 15%).

**Prior.** Dirichlet concentration `α_i = κ · w_i`, with default `κ = 400`: strong enough
that an empty-data draw stays near the published proportions, weak enough that observed
history visibly shifts it.

**Posterior.** With reference/practice-form counts `n_i`, sampling uses
`Dirichlet(α + n)`: i.e. `α_i = κ·w_i + n_i` per leaf. Counts can be fed via
`BlueprintModel(kappa=..., observations={cell: count})` (tested:
`test_blueprint.test_posterior_shifts_toward_observed_skill`).

**Draw.**
1. Sample proportions `π ~ Dirichlet(α)` using the Gamma trick
   (`π_i = γ_i/Σγ`, `γ_i ~ Gamma(α_i, 1)`).
2. Expected counts `N·π`.
3. **Hamilton apportionment** (largest-remainder rounding): floor every cell, then hand
   out the remaining seats in descending fractional-part order (ties broken by lower
   index), so counts sum to *exactly* N: 27/module for R&W, 22/module for Math.

Everything is seeded, so identical inputs reproduce byte-identical blueprints.

### Model 2: Ability estimator (`satprep/core/ability.py`)

**Response model (2PL).** `P(u=1 | θ) = σ(a·(θ − b))`, where `a > 0` is item
discrimination and `b` is difficulty. Every generated question carries `(a, b)` drawn
from its difficulty band (easy `b ∈ [−2.0, −0.7]`, medium `[−0.5, 0.6]`,
hard `[0.8, 2.2]`, `a ∈ [1.0, 1.6]`).

**Estimation.** MAP under a Gaussian prior `θ ~ N(0, 1)`:

```
ℓ(θ)     = Σᵢ [uᵢ log pᵢ + (1−uᵢ) log(1−pᵢ)] − θ²/2      (pᵢ = σ(aᵢ(θ−bᵢ)))
ℓ′(θ)    = Σᵢ aᵢ(uᵢ − pᵢ) − θ
ℓ″(θ)    = −Σᵢ aᵢ² pᵢ(1−pᵢ) − 1        < 0  ∀θ  ⇒ strictly concave ⇒ unique max
```

Maximized by **safeguarded Newton-Raphson** (backtracking line search on ℓ, so steps
never decrease the posterior even in flat regions). The prior guarantees finite θ̂ even
for all-correct/all-wrong runs. Posterior sd uses the Laplace approximation
`sd = 1/√(Σ a²pq + 1)` at θ̂.

One θ̂ is tracked **per (user, skill)**; section aggregates are attempt-weighted means.
MAP depends only on the multiset of responses, so replaying stored responses rebuilds
identical estimates after restart (the API does exactly this).

**Item selection.** Next question = unanswered item maximizing Fisher information
`I(θ̂) = a²·p·q` given the current per-skill θ̂: items cluster near the learner's
ability, where they are most informative (a lightweight CAT policy).

**Module-2 branching.** After module 1: percent-correct `< 50%` → easy-leaning module 2,
`50–75%` → balanced, `≥ 75%` → hard-leaning (difficulty-profile priors
55/40/5, 30/45/25, 5/35/60 respectively). Thresholds are documented assumptions that
qualitatively mirror the real digital SAT's between-module adaptivity.

### Difficulty calibration of the question bank

Difficulty in this project is **the IRT `b` parameter**, not a cosmetic label. Every
generated item draws `(a, b)` from a tier-specific band: easy `b ∈ [−2.0, −0.7]`,
medium `[−0.5, 0.6]`, hard `[0.8, 2.2]`, with discrimination `a ∈ [1.0, 1.6]`: so
blueprint difficulty tiers translate directly into response-probability behavior:
`P(correct) = σ(a(θ − b))`. A "hard" item is one whose b sits well above your θ.

Content difficulty is then *constructed* to match the band, not just claimed:

- **Math tiers change structure, not just numbers.** Easy linear equations are
  `ax + b = c`; medium adds distribution (`p(x + q) = r`) or radical forms; hard adds
  variable-on-both-sides systems of terms. Equivalent expressions moves from FOIL to
  exponent rules to binomial squares / power-of-power families; trigonometry scales
  Pythagorean triples and varies which ratio is requested; geometry asks either
  hypotenuse or leg at medium.
- **Distractors are common errors, not noise.** Wrong choices encode specific
  mistakes: sign flips and swapped ordered pairs in systems, no-flip when dividing an
  inequality by a negative, perimeter-instead-of-area, diameter instead of radius,
  reciprocal trig ratios, adding exponents where the rule says multiply, forgetting
  the ÷60 in rate conversions. Plausible-but-wrong is what makes an item test the
  skill rather than elimination-guessing.
- **R&W items are authored per tier with explicit cue logic.** Each template carries
  its own cue ("yet", "far from", "so...that") and an explanation naming why the key
  fits and each distractor cannot; pools were sized so a single session never repeats
  a prompt (bank-level dedup enforces this deterministically).
- **Verification, not vibes**: `tools/content_audit.py` generates dozens of items per
  skill × tier and reports uniqueness rates and structural validity (4 unique
  choices, valid answer index); `tests/test_bank_generators.py` asserts every
  framework skill is generatable at every tier and that empirical `b` values respect
  their bands.

### Seeding scheme (`core/rng.py`)

- Every stochastic component derives an independent stream:
  `seed = SHA-256("part1:part2:…")[:8 bytes] as int` → `random.Random(seed)`.
- Item streams include the blueprint's own seed as salt, so two blueprints can never
  produce colliding question ids or content.
- Given equal inputs (user request + seed), blueprints, questions, and ordering are
  fully deterministic. The API returns the generated seed so any session can be
  reproduced later.

### Score scale (`scoring/scale.py`)

Heuristic, **documented-as-heuristic** piecewise-linear map from section mean θ to a
200–800 band (anchors: −2.5→300, −1→430, 0→530, 1→630, 2.5→740), band half-width
`clamp(60/√n, 15..80)/2`. This is *not* College Board equating and should be read as a
rough progress indicator only.

## Architecture

See [`ARCHITECTURE.md`](ARCHITECTURE.md) for the full file tree, data flow diagram,
stage-by-stage rationale, measured performance numbers, and scaling notes. The UI's
design system (tokens, bracket/tick grammar, motion rules) is documented separately
in [`DESIGN.md`](DESIGN.md). In short:

```
framework.py ──► blueprint.py ──► bank.py ──► engine/session.py | engine/mocktest.py
                    ▲                                  │
                    │            ability.py ◄──────────┘
                    └──── storage/db.py ◄── api/server.py ◄─► web/ (vanilla JS SPA)
```

Strict layer separation: core models are pure functions of their inputs (no I/O),
generation is deterministic given seeds, orchestration never touches math internals,
and persistence/API know nothing about either model's equations.

## API overview

| Method & path                        | Purpose |
|--------------------------------------|---------|
| `POST /api/users {name}`             | Create local profile |
| `GET  /api/meta/config`              | Server config for the UI (Google client id if set) |
| `POST /api/auth/google {credential}` | Verify a Google ID token; return mapped account |
| `GET  /api/users/{id}`               | Profile + θ snapshot + score bands |
| `GET  /api/meta/framework`           | Framework tree for the UI |
| `POST /api/practice {user_id, section?, skills?, length?, seed?}` | Start adaptive session |
| `GET  /api/sessions/{id}/next`       | Serve next max-information item |
| `POST /api/sessions/{id}/answer {choice_index}` | Grade + IRT update |
| `GET  /api/sessions/{id}/summary`    | Per-skill summary |
| `POST /api/mocks {user_id, sections?, seed?}` | Assemble timed mock (module 1s) |
| `GET  /api/mocks/{id}`               | Mock state (module 2 appears after module 1) |
| `POST /api/mocks/{id}/answer`        | Grade + branch module 2 when ready |
| `GET  /api/mocks/{id}/report`        | Module results + score bands |
| `GET  /api/dashboard/{user_id}`      | θ trends, accuracy buckets, history |

Questions are served **without** `answer_index`/`explanation`; those are revealed only
by the answer endpoints.

## Assumptions & limitations (v1)

1. Framework percentages/skill splits are author-encoded approximations of public
   specs; exact mixes are proprietary to College Board.
2. Difficulty-tier priors and branching thresholds (50%/75%) are assumptions.
3. The θ→score mapping is heuristic, not psychometrically equated.
4. R&W items come from original micro-passage templates: they exercise the named
   skills but are stylistically simpler than exam passages. Pools are finite by
   design; within one session the bank never repeats a prompt when pool capacity
   allows (`QuestionBank` deterministic dedup).
5. Single-process SQLite behind one lock; **completed** summaries and every response
   persist, while active sessions live in memory: a server restart ends in-flight
   sessions by design. Client refreshes resume cleanly because `/next` is idempotent
   while a question is pending. Concurrency: all mutating routes serialize on
   `AppState.lock`; measured load behavior is recorded in `ARCHITECTURE.md`.
6. No authentication: user identity is a localStorage id (fine for local use).
7. Mock timers display countdown but do not force-submit at expiry: this is
   deliberate: auto-filling or voiding unanswered items on expiry would distort θ
   data. The timer reads `TIME EXPIRED: FINISH MODULE` and the module stays open.

## Scaling path

- **Postgres**: swap `storage/db.py`; its DAO surface is small and SQL-only.
- **Multi-user/auth**: add token middleware in `api/server.py`; engines unchanged.
- **Question volume**: replace on-demand generation inside `bank.py` with a cached,
  deduplicated pre-generated bank behind the same interface.
- **Richer IRT**: the estimator accepts arbitrary `(a, b)` lists: adding a 3PL or
  Elo fallback requires no changes outside `core/ability.py`.
