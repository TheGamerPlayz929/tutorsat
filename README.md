# TutorSat

**Live site: [https://tutorsat.web.app](https://tutorsat.web.app/)**

A full-stack SAT-style practice platform with adaptive question selection,
timed mock exams with section branching, per-skill ability tracking, and a
progress dashboard.

> ## ⚠️ Disclaimer

> **No College Board question content is included, scraped, or reproduced.** All

> software. Framework percentages are author-encoded approximations of publicly
> documented specifications.

## Quick start

Requires **Python 3.10+** (standard library only: zero dependencies).

```bash
python run.py                # serves http://127.0.0.1:8765
python run.py --port 9000 --db mydata.db
```

Open http://127.0.0.1:8765 in a browser: create a profile → practice → mock → dashboard.

Run the test suite:

```bash
python -m unittest discover -s tests -v
```

Reset all data by deleting `satprep.db`.

### Deploying to a server

See [`DEPLOYMENT.md`](DEPLOYMENT.md) for step-by-step guides: Docker Compose
with a bundled Caddy/nginx TLS proxy, bare-metal systemd, Dockerfile platforms
(Fly/Railway/Render/Cloud Run), and two $0-no-credit-card stacks (PythonAnywhere
alone, or Cloudflare Pages / Firebase Hosting frontend + free backend), plus a
combo-selection table, backup guidance, security-checklist, and single-instance
constraints.

### Optional: Google Sign-In

Local profiles work out of the box. If you want Google account sign-in:

1. Create an OAuth **client ID** (type: Web application) in Google Cloud Console,
   and add your serving origins to its **Authorized JavaScript origins**.
2. Start the server with it:
   `python run.py --google-client-id YOUR_CLIENT_ID.apps.googleusercontent.com`
   or set the `GOOGLE_CLIENT_ID` environment variable.
3. The onboarding screen gains a "Sign in with Google" button. Progress is
   mapped to a stable account id, so your history follows you across devices
   on the same deployment. All data stays in your deployment's own database.

## How it works (overview)

- **Blueprint composition** — every practice session and mock module is sampled
  from a statistical model over the published digital SAT framework
  (sections → domains → skills), so content mix tracks the real exam's
  documented proportions rather than uniform randomness.
- **Adaptive selection** — a per-skill ability estimate is maintained for every
  learner and updated after each response. Question choice is driven by an
  item-response-theory selection rule that serves items near the learner's
  current level, where they are most informative.
- **Item calibration** — new items start from a neutral prior; as response
  data accumulates, item parameters are re-estimated from actual learner
  performance (batch calibration job included under `satprep/calibration/`).
- **Mock exams** — two-section timed mocks whose second module branches on
  first-module performance, mirroring the digital SAT's adaptive structure.
- **Deterministic generation** — all randomness is seeded; any session can be
  reproduced exactly from its seed.

Detailed design notes are intentionally not published in this README. See the
source under `satprep/` (module docstrings explain each layer) if you want the
full picture.

## Architecture

See [`ARCHITECTURE.md`](ARCHITECTURE.md) for the file tree, data flow, and
scaling notes. In short:

```
framework.py ──► blueprint.py ──► bank.py ──► engine/session.py | engine/mocktest.py
                    ▲                                  │
                    │            ability.py ◄──────────┘
                    └──── storage/db.py ◄── api/server.py ◄─► web/ (vanilla JS SPA)
```

Strict layer separation: core models are pure functions of their inputs (no I/O),
generation is deterministic given seeds, orchestration never touches math internals,
and persistence/API know nothing about either model's internals.

## API overview

| Method & path                        | Purpose |
|--------------------------------------|---------|
| `POST /api/users {name}`             | Create local profile |
| `GET  /api/meta/config`              | Server config for the UI (Google client id if set) |
| `POST /api/auth/google {credential}` | Verify a Google ID token; return mapped account |
| `GET  /api/users/{id}`               | Profile + ability snapshot + score bands |
| `GET  /api/meta/framework`           | Framework tree for the UI |
| `POST /api/practice {user_id, section?, skills?, length?, seed?}` | Start adaptive session |
| `GET  /api/sessions/{id}/next`       | Serve next item |
| `POST /api/sessions/{id}/answer {choice_index}` | Grade + ability update |
| `GET  /api/sessions/{id}/summary`    | Per-skill summary |
| `POST /api/mocks {user_id, sections?, seed?}` | Assemble timed mock (module 1s) |
| `GET  /api/mocks/{id}`               | Mock state (module 2 appears after module 1) |
| `POST /api/mocks/{id}/answer`        | Grade + branch module 2 when ready |
| `GET  /api/mocks/{id}/report`        | Module results + score bands |
| `GET  /api/dashboard/{user_id}`      | Ability trends, accuracy buckets, history |

Questions are served **without** `answer_index`/`explanation`; those are revealed only
by the answer endpoints.

## Assumptions & limitations (v1)

1. Framework percentages/skill splits are author-encoded approximations of public
   specs; exact mixes are proprietary to College Board.
2. The score-band mapping is heuristic, not psychometrically equated; read it as a
   rough progress indicator.
3. R&W items come from original micro-passage templates: they exercise the named
   skills but are stylistically simpler than exam passages.
4. Single-process SQLite behind one lock; **completed** summaries and every response
   persist, while active sessions live in memory: a server restart ends in-flight
   sessions by design. Client refreshes resume cleanly because `/next` is idempotent
   while a question is pending.
5. No authentication beyond optional Google sign-in: local identity is a
   browser-stored id (fine for personal and small-group use).
6. Mock timers display countdown but do not force-submit at expiry: this is
   deliberate: auto-filling or voiding unanswered items on expiry would distort
   ability data.
